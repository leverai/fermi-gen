## Overview

The `fermi-db` package owns the database schema and migrations. We use Alembic with async PostgreSQL and `uv` for package management.

**Key Points:**
- Alembic project lives under `packages/fermi-db/alembic`
- All commands run via `uv` with `--package fermi-db` flag
- `DATABASE_URL` must point to an existing PostgreSQL database
- Initial migration creates all tables and the `pgvector` extension
- Migrations are tracked in the `alembic_version` table

## Setup

### Prerequisites

1. **PostgreSQL Database**: Must exist before running migrations
2. **pgvector Extension**: Installed via migration (or manually by superuser)
3. **Environment Variable**: `DATABASE_URL` must be set

### One-Time Setup

1. **Install dependencies** (from workspace root):
   ```bash
   uv sync --all-packages
   ```

2. **Set DATABASE_URL**:
   ```bash
   export DATABASE_URL=postgresql+asyncpg://user:password@localhost:5432/fermi-db
   ```

3. **Run initial migration**:
   ```bash
   uv run --package fermi-db alembic -c alembic.ini upgrade head
   ```

   This creates:
   - `pgvector` extension
   - All tables (including `fermi`)
   - Indexes and constraints

## Common Commands

All commands are run from the **workspace root** using `uv run --package fermi-db`.

### Check Current Version

```bash
uv run --package fermi-db alembic -c alembic.ini current
```

### Show Migration History

```bash
uv run --package fermi-db alembic -c alembic.ini history
```

### Upgrade to Latest

```bash
uv run --package fermi-db alembic -c alembic.ini upgrade head
```

### Downgrade One Revision

```bash
uv run --package fermi-db alembic -c alembic.ini downgrade -1
```

**⚠️ Warning:** Downgrades can cause data loss. Use with caution in production.

### Show SQL for Upgrade

```bash
uv run --package fermi-db alembic -c alembic.ini upgrade head --sql
```

## Creating Migrations

### Automatic Migration Generation

Alembic can detect model changes and generate migrations automatically:

```bash
uv run --package fermi-db alembic -c alembic.ini revision --autogenerate -m "your descriptive message"
```

**Example:**

```bash
uv run --package fermi-db alembic -c alembic.ini revision --autogenerate -m "add provider column to questions"
```

This creates a new migration file in `packages/fermi-db/alembic/versions/`.

### Manual Migration Creation

For complex changes or when autogenerate isn't sufficient:

```bash
uv run --package fermi-db alembic -c alembic.ini revision -m "your descriptive message"
```

Then edit the generated file to add your `upgrade()` and `downgrade()` functions.

### Best Practices

1. **Descriptive names**: Use clear, specific migration messages
2. **Small changes**: One logical change per migration
3. **Review generated SQL**: Always check autogenerated migrations
4. **Test downgrades**: Ensure `downgrade()` functions work
5. **Import all models**: Keep `alembic/env.py` imports up to date

## Applying Migrations

### Development Environment

```bash
# Set local database URL
export DATABASE_URL=postgresql+asyncpg://postgres:postgres@localhost:5432/fermi-db

# Apply migrations
uv run --package fermi-db alembic -c alembic.ini upgrade head
```

### Production Environment

**Using Cloud SQL Proxy:**

```bash
# Start proxy
cloud-sql-proxy guesstimate-5483f:us-central1:your-instance

# In another terminal
export DATABASE_URL=postgresql+asyncpg://user:password@127.0.0.1:5432/fermi-db
uv run --package fermi-db alembic -c alembic.ini upgrade head
```

**Direct Connection (if public IP enabled):**

```bash
export DATABASE_URL=postgresql+asyncpg://user:password@PUBLIC_IP:5432/fermi-db
uv run --package fermi-db alembic -c alembic.ini upgrade head
```

### Docker Environment

```bash

export DATABASE_URL=postgresql+asyncpg://postgres:postgres@localhost:5433/fermi-db
uv run --package fermi-db alembic -c alembic.ini upgrade head
```

## CI/CD Integration

### GitHub Actions

Migrations are applied automatically in CI/CD workflows before deploying services.

**Example workflow step:**

```yaml
- name: Run Database Migrations
  env:
    DATABASE_URL: ${{ secrets.DATABASE_URL }}
  run: |
    uv run --package fermi-db alembic -c alembic.ini upgrade head
```

### Local CI Testing

Before pushing, test migrations with a clean database:

```bash
# Start test database
docker run --rm -d \
  --name postgres-test \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=fermi-db \
  -p 5433:5432 \
  pgvector/pgvector:pg17

# Apply migrations
export DATABASE_URL=postgresql+asyncpg://postgres:postgres@localhost:5433/fermi-db
uv run --package fermi-db alembic -c alembic.ini upgrade head

# Run tests
make test-etl-integration

# Cleanup
docker stop postgres-test
```

### Pre-Deployment Checklist

- [ ] Migrations tested locally with fresh database
- [ ] Migrations tested with existing data (if modifying tables)
- [ ] Downgrade tested (if needed)
- [ ] Breaking changes documented
- [ ] Team notified of schema changes

## Naming Conventions

### Migration File Names

Alembic automatically generates timestamped filenames:

```
YYYYMMDDHHMMSS_your_message.py
```

Example: `20251105120000_add_provider_column.py`

### Constraint and Index Names

For stable, predictable names across environments, use explicit naming:

```python
# Good: Explicit constraint name
op.create_unique_constraint(
    'uq_fermi_answers_question_id',
    'fermi_answers',
    ['question_id']
)

# Bad: Auto-generated name (unpredictable)
op.create_unique_constraint(
    None,  # Alembic generates random name
    'fermi_answers',
    ['question_id']
)
```

### Shared Naming Convention (Future Enhancement)

For consistent naming across all constraints and indexes, define a `MetaData` with naming convention:

```python
# In fermi_db/models/__init__.py
from sqlalchemy import MetaData

convention = {
    "ix": "ix_%(column_0_label)s",
    "uq": "uq_%(table_name)s_%(column_0_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s"
}

metadata = MetaData(naming_convention=convention)

# Then update all SQLModel classes to use this metadata
```

## Troubleshooting

### Issue: `CREATE EXTENSION vector` Error

**Error:**
```
ERROR: could not open extension control file ".../vector.control": No such file or directory
```

**Cause:** `pgvector` not installed in PostgreSQL.

**Solutions:**

**For Docker:**
```bash
# Use pgvector image
docker run --rm -d \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=fermi-db \
  -p 5433:5432 \
  pgvector/pgvector:pg17
```

**For macOS (Homebrew):**
```bash
brew install pgvector
```

**For Ubuntu/Debian:**
```bash
sudo apt-get install postgresql-17-pgvector
```

**For existing PostgreSQL (superuser):**
```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

### Issue: Autogenerate Misses Tables/Columns

**Error:** Autogenerate doesn't detect new models or columns.

**Cause:** Models not imported in `alembic/env.py`.

**Solution:** Ensure all models are imported:

```python
# In packages/fermi-db/alembic/env.py
from fermi_db.models import (
    Seed,
    RawQuestion,
    FermiQuestion,
    FermiAnswer,
    SeedsUsage,
    # ... all other models
)
```

### Issue: Enum Type Already Exists

**Error:**
```
ERROR: type "status_enum" already exists
```

**Cause:** Enum type created in previous migration.

**Solution:** Use conditional creation:

```python
# In migration upgrade()
from sqlalchemy import Enum
from sqlalchemy.dialects.postgresql import ENUM

# Drop enum if exists (in downgrade)
op.execute("DROP TYPE IF EXISTS status_enum")

# Create enum conditionally (in upgrade)
op.execute("""
    DO $$ BEGIN
        CREATE TYPE status_enum AS ENUM ('pending', 'unique', 'duplicate');
    EXCEPTION
        WHEN duplicate_object THEN null;
    END $$;
""")
```

### Issue: Row Object Return Bug

**Error:**
```
TypeError: 'Row' object is not subscriptable
```

**Cause:** SQLAlchemy query returns `Row` objects, not tuples.

**Solution:**

```python
# Bad
result = session.execute(select(Question.id))
ids = [id for id in result.all() if id is not None]

# Good
result = session.execute(select(Question.id))
rows = result.all()
ids = [row[0] for row in rows if row[0] is not None]
```

### Issue: Foreign Key Constraints to `fermi` Table

**Note:** As of December 2025, `fermi` is now a regular table (not a materialized view), so foreign key constraints are fully supported.

**Adding FK constraints:**

```sql
ALTER TABLE user_question_history ADD CONSTRAINT fk_user_history_fermi 
  FOREIGN KEY (question_uid) REFERENCES fermi(uid);
ALTER TABLE answer_events ADD CONSTRAINT fk_answer_events_fermi 
  FOREIGN KEY (question_uid) REFERENCES fermi(uid);
ALTER TABLE questions_votes ADD CONSTRAINT fk_questions_votes_fermi 
  FOREIGN KEY (question_uid) REFERENCES fermi(uid);
```

### Issue: Migration Conflicts

**Error:**
```
ERROR: multiple heads detected
```

**Cause:** Multiple developers created migrations simultaneously.

**Solution:**

```bash
# Show all heads
uv run --package fermi-db alembic -c alembic.ini heads

# Merge heads
uv run --package fermi-db alembic -c alembic.ini merge heads -m "merge conflicting migrations"
```

### Issue: `DATABASE_URL` Not Found

**Error:**
```
ERROR: The DATABASE_URL environment variable is not set
```

**Solution:**

```bash
# Set environment variable
export DATABASE_URL=postgresql+asyncpg://user:password@host:port/dbname

# Or use .env file
echo "DATABASE_URL=postgresql+asyncpg://user:password@host:port/dbname" > .env
```

## Recent Bug Fixes

### Fixed: Row Object Return Bug (2025-11-04)

**Issue:** `get_latest_unanswered_questions()` returned `Row` objects instead of integers, causing query errors.

**Fix:** Changed from:

```python
return cast(list[int], [id for id in result.all() if id is not None])
```

To:

```python
rows = result.all()
return [row[0] for row in rows if row[0] is not None]
```

**Impact:** Fixed integration tests and answer service functionality.

### Updated: Converted `fermi` from Materialized View to Table (2025-12-13)

**Change:** The `fermi` materialized view was converted to a regular table to support proper foreign key constraints.

**Migration Details:**
- Dropped the materialized view `fermi`
- Created a new `fermi` table with the same schema
- Added foreign key constraint from `fermi.id` to `fermi_questions(id)`
- Updated ETL pipeline to use `sync_fermi_table()` for inserting rows
- Foreign key constraints from `user_question_history`, `answer_events`, and `questions_votes` can now be added

**Benefits:**
- Proper referential integrity with FK constraints
- No need for manual `REFRESH MATERIALIZED VIEW` commands
- Simpler data management in ETL pipeline

**Impact:** The ETL service now calls `sync_fermi_table()` after enrichment to populate the `fermi` table with newly enriched questions.
